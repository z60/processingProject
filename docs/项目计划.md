## 1. 目标与范围

### 1.1 项目目标

把工单处置中「分类 → 查数据 → 写摘要 → 判断转不转人工」四段重复劳动交给 AI，最终处置决定仍由人工确认。对应需求文档 2.2 的三条硬目标：

1. **效率**：AI 接管分类、查询、摘要、转人工初判；人工只做确认与高风险处置。
2. **质量**：高风险场景转人工触发率 100%，路由首次正确率 MVP ≥ 90%。
3. **边界**：不自动执行资金操作、不自动作出处置决定、写操作必须人工审批。

### 1.2 MVP（v1）范围

| 模块 | 纳入 v1 | 说明 |
|---|---|---|
| 接入与路由（F-01~F-05） | ✅ | `/api/chat`、`/api/ticket`，缓存、路由、追问、风险标记规则 |
| 专家 Agent（F-06、F-09） | ✅ | 结构化查询专家 + 上下文隔离；知识问答专家（F-07）为 P1，v1 保留链路 |
| 合规检测（F-08） | ✅ | 禁止承诺检测以确定性规则 + 合规专家双层实现 |
| 转人工（F-10~F-12、F-14） | ✅ | 代码级规则引擎、`HANDOFF` 一等状态、工单打包、失败计数器 |
| 人工工作台（F-13） | ⚠️ 只读骨架 | v1 提供查询与动作回写接口，前端留到 v3 |
| 审计与回放（F-15、F-16） | ✅ | 字段级落库 + 按 trace_id 回放 |
| 三层埋点与看板（F-17、F-18） | ⚠️ 埋点数据先落审计表 | 看板 UI 留到 v3 |
| 评测门禁（F-19、F-20） | ✅ | 15 条回归集 + `FAIL` 门禁脚本 |
| Checkpoint 与幂等（F-22、F-23） | ✅ | LangGraph SQLite Checkpointer；写操作幂等键 |

### 1.3 明确不做

- 不自动退款、不自动减免、不自动调额、不自动关闭工单。
- 不接真实 ERP：全部使用 `conf/seed/` 合成数据。
- 不存储真实用户敏感信息；回归集样本脱敏后入库。
- 不做人工工作台前端（v1 只提供接口）。

## 3. 总体架构

### 3.1 分层架构

```
              ┌──────────────── FastAPI (app/api) ────────────────┐
              │ /api/chat  /api/ticket  /api/audit  /api/handoff   │
              │ /api/eval  /healthz                                │
              └───────────────┬───────────────────────────────────┘
                              │ DTO ↔ Entity
              ┌───────────────▼─────────────── service ────────────┐
              │ agent_service   ticket_service  audit_service     │
              │ eval_service                                       │
              └──────┬───────────────┬───────────────┬────────────┘
                     │               │               │
      ┌──────────────▼─── agent ────┴── repository ──┴─── client ──┐
      │ graph / nodes /  │  ticket/order/audit/     │ mysql_client  │
      │ tools / state    │  knowledge/cache          │ qdrant_client │
      │ (LangGraph)      │  ← entity / mapper       │ embedding     │
      │                  │                          │ llm / mcp     │
      └──────────────────┴──────────────────────────┴───────────────┘
```

## 4. 多智能体与 MCP 设计

### 4.1 LangGraph 节点图

```
Entry → router ──低置信/多意图──→ clarify ──超过 N 轮──→ guard
          │                                    └→ 输出追问
          ├──order 意图──────→ order_expert ─────┐
          ├──knowledge 意图──→ knowledge_expert ─┼→ guard ──命中规则──→ handoff ──→ audit → End
          └──refund/risk────→ compliance_expert ┘         └─未命中──→ audit → End
```

| 节点 | 职责 | 是否调 LLM | 关键约束 |
|---|---|---|---|
| `router` | 输出 `intent` / `confidence` / `risk_flag` / `slots` | 是（结构化输出） | JSON 解析失败重试 1 次，再失败落 `unknown` + 兜底追问 |
| `clarify` | 低置信度/多意图冲突时追问一轮 | 是（可离线模板兜底） | 累计追问 ≤ 3 轮，超限交规则引擎 |
| `order_expert` | 订单/工单进度结构化查询 | 是 + 工具 | 只允许 `query_order` / `query_ticket`，禁止编造，查无记录如实反馈 |
| `knowledge_expert` | 制度条款/售后政策问答 | 是 + 工具 | 只允许 `search_knowledge`；最高分低于阈值时输出「未找到相关制度条款」 |
| `compliance_expert` | 资金/法律/隐私类风险处置建议 | 是 + 工具 | 不输出最终处置，只给摘要与建议草稿 |
| `guard` | 确定性规则引擎 | **否** | 三类强制转人工 + 两条补充规则（回复禁止承诺、用户升级信号）、无依据拒答；模型无转人工发言权 |
| `handoff` | 打包转人工工单（会话快照、槽位、触发原因、建议草稿） | 是（摘要） | 工单落库 + TTL 缓存双写，服务重启不丢 |
| `audit` | 逐节点审计事件落库 | 否 | 关键字段缺失即视为缺陷 |

### 4.2 Agent State（`app/agent/state.py`）

| 字段 | 类型 | 说明 |
|---|---|---|
| `trace_id` / `session_id` / `user_id` / `text` | str | 链路追踪与输入 |
| `intent` / `confidence` / `risk_flag` / `slots` | str / float / bool / dict | 路由结果 |
| `clarify_rounds` | int | 连续未解决计数（F-14） |
| `expert` / `draft` / `citations` | str / str / list | 专家产出 |
| `tool_calls` / `tokens` | list / dict | 工具轨迹与 token 统计（F-15/F-17） |
| `handoff` / `handoff_reason` | bool / dict | 规则引擎结论（模型不可写） |
| `status` | str | `ANSWERED` / `CLARIFY` / `HANDOFF` |

### 4.3 MCP 工具网关

MCP server 以 stdio 方式由 `app/client/mcp_server.py` 拉起，工具集合固定为 4 个，全部只读：

| MCP 工具 | 入参 | 出参 | 使用方 |
|---|---|---|---|
| `query_order` | `order_no` | 订单实体或 `NOT_FOUND` | order_expert |
| `query_user_orders` | `user_id`, `limit` | 订单列表（脱敏） | order_expert |
| `query_ticket` | `ticket_id` | 工单状态 | order_expert |
| `search_knowledge` | `query`, `top_k` | 命中分块（含 score / source） | knowledge_expert |

约束：
- 专家节点通过 `app/agent/tools.py` 的 `execute_tool` 调用 MCP，每次调用写入 `tool_calls`，审计可回放。
- MCP server 不可用时专家节点降级为「业务系统不可用」如实反馈，不编造数据。
- v1 不暴露任何写工具；写操作一律走人工工作台接口 + 幂等键。

## 5. 数据设计

### 5.1 MySQL（`project1028`）

| 表 | 主键 | 关键字段 | 说明 |
|---|---|---|---|
| `orders` | `id` | `order_no`(uk)、`user_id`、`status`、`amount`、`refundable_amount`、`logistics_no`、`created_at`、`updated_at` | 合成订单/事务数据，只读 |
| `tickets` | `ticket_id` | `session_id`、`user_id`、`trace_id`、`intent`、`confidence`、`risk_flag`、`raw_input`、`summary`、`draft_reply`、`status`、`handoff_reason`、`created_at`、`updated_at` | 每轮处置结果 |
| `handoff_tickets` | `id` | `ticket_id`(uk)、`trigger_type`、`trigger_detail`(JSON)、`conversation_snapshot`(JSON)、`slots`(JSON)、`draft_reply`、`status`、`handler_action`、`handler_note`、`created_at`、`handled_at` | 转人工工单，人工工作台数据源 |
| `audit_logs` | `id` | `trace_id`(idx)、`node`、`event`、`intent`、`confidence`、`tool_calls`(JSON)、`retrieval_sources`(JSON)、`handoff_trigger`(JSON)、`latency_ms`、`token_usage`(JSON)、`prompt_version`、`created_at` | 审计回放数据源 |
| `regression_cases` | `case_id` | `category`、`input_text`、`expected_status`、`expected_intent`、`assertions`(JSON)、`source_version` | 与 `conf/regression_cases.jsonl` 同步 |
| `idempotency_keys` | `idem_key`(uk) | `scope`、`result_ref`、`created_at` | 写操作幂等（F-23） |

索引策略：`orders(order_no)`、`orders(user_id)`、`tickets(session_id, created_at)`、`audit_logs(trace_id)`、`handoff_tickets(status)`。

### 5.2 Qdrant 集合

| 项 | 值 |
|---|---|
| 集合名 | `knowledge_chunks` |
| 向量 | size = **1024**，distance = **Cosine** |
| payload | `doc_id`、`title`、`category`（loan_after / annuity / ecommerce）、`chunk_index`、`text`、`source`、`version` |
| ID | UUID（确定性：`uuid5(doc_id:chunk_index)`，重复初始化幂等） |
| 检索 | `query_points` + `score_threshold`（`conf/settings.json` → `knowledge.min_score`） |
| 降级 | 集合为空时知识专家输出「未找到相关制度条款」并记录审计 |

## 6. 接口设计

| 方法 | 路径 | 说明 | 返回要点 |
|---|---|---|---|
| POST | `/api/chat` | 对话入口 | `trace_id`、`status`(ANSWERED/CLARIFY/HANDOFF)、`reply`、`intent`、`confidence`、`risk_flag`、`citations`、`handoff`、`latency_ms` |
| POST | `/api/ticket` | 工单提交入口 | 同上 + `ticket_id` |
| GET | `/api/audit/{trace_id}` | 审计回放 | 按时间排序的节点时间线、`handoff_trigger` 证据链 |
| GET | `/api/handoff` | 转人工工单列表 | `status` 过滤（OPEN/CONFIRMED/RETURNED） |
| POST | `/api/handoff/{id}/action` | 人工动作（确认/退回/修改） | 幂等键校验 + 审计回写 |
| POST | `/api/eval/regression` | 跑回归集 + 质量门禁 | `pass_rate`、`gate`(PASS/FAIL)、逐条结果 |
| GET | `/healthz` | 依赖健康检查 | MySQL / Qdrant / Embedding 三项探测结果 |

```json
  "citations": [],
  "handoff": {"ticket_id": "H-1028-0001", "trigger_type": "refund_gray_zone",

}
```

## 7. 非功能实现要点

| 需求 | 落地方式 |
|---|---|
| P95 延迟基线 | `latency_ms` 与节点耗时写审计表，v1 只记录不设门禁 |
| 缓存命中零 token | `cache_repository` 以 `sha256(user_id + 归一化文本)` 为键，命中直接返回，不进入图 |
| 故障恢复 | LangGraph `SqliteSaver`（`data/checkpoint.sqlite3`），`thread_id = session_id`，按节点恢复 |
| 幂等 | 写接口按 `sha256(user_id + action + 内容指纹)` 去重，`idempotency_keys` 表兜底 |
| 审计完整性 | `audit_service` 统一封装；MySQL 不可用时降级写 `data/audit_fallback.jsonl` 并告警日志，不丢事件 |
| 配置外置 | 阈值/规则/意图/门禁全部在 `conf/*.json`，不硬编码 |
| 密钥安全 | 连接串与 API Key 走 `.env`；`.env.example` 不含真实凭据；`.env` 加入 `.gitignore` |
| Prompt 版本 | `prompts/` 文件头部 `version` 字段写入审计 `prompt_version` |
| 可观测 | 三层埋点先落审计表：HTTP 入口耗时、节点耗时、工具调用轨迹（含参数摘要与耗时） |

## 9. 质量门禁与测试

### 9.1 回归集设计（15 条，`conf/regression_cases.jsonl`）

| 场景 | 条数 | 断言重点 |
|---|---|---|
| 知识问答 | 4 | 引用来源非空；低分用例断言拒答话术 |
| 结构化查询 | 4 | 命中订单；查无记录断言不编造 |
| 高风险/资金 | 4 | `status=HANDOFF`、`trigger_type` 正确、无金额承诺话术 |
| 边界（低置信/多意图/情绪） | 3 | 追问或转人工；`clarify_rounds` 计数正确 |

### 9.2 门禁规则（F-20）

- 高风险用例漏转 **> 0 → FAIL**，阻断发布。
- 审计关键字段（`trace_id`/`node`/`event`）缺失，或转人工用例缺少 `handoff_trigger` 证据 → FAIL。
- 总通过率 < 93% → FAIL。

### 9.3 自检

- `app/script/selftest.py`：规则引擎、指纹/幂等、缓存 TTL、mapper 往返、Qdrant 检索连通、知识拒答阈值。
- 每个非平凡模块（规则引擎、路由、幂等、审计）保留 `assert` 级自检，随代码一起交付。

## 12. 运行与运维

```bash
# 1. 依赖
pip install -r requirements.txt
# 2. 配置
copy .env.example .env    # 填入 MySQL / Qdrant / Embedding / LLM 参数
```
